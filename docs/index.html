STARWAKE の内部で
使っているアルゴリズムと技術

地表 1 m の凹凸から数光年先の恒星までを、ひと続きの空間として飛べるようにするための仕組みを、章ごとに「何が問題か → どう解いたか → 実装の要点 → 割り切った点」の順で説明します。

図の中の「動かせるデモ」は、ゲーム本体のコードをそのまま読み込んで動いています。python serve.py で起動し、http://localhost:5173/docs/ から開いてください。

このページはファイルを直接開いているため、ゲーム本体のコードを読み込むデモ (銀河・地形) は動きません。

0全体像

ビルドなしの ES モジュールと Three.js だけで、約 8,000 行。

src/main.jssrc/game.js

ブラウザが index.html を読み、import map で Three.js (0.170) を CDN から取得し、src/main.js が Game を 1 つ作って開始します。バンドラーもトランスパイラーも使っていません。

1 フレームの流れ

  1. 入力をまとめて操縦入力 (ピッチ・ヨー・ロール・スロットルなど、すべて −1〜1) にする。
  2. 物理を 1/120 秒刻みで必要な回数だけ進める。環境 (重力・空気密度) を求め、推力・空気力・接地反力をかけて積分し、座標系の切り替えと原点の付け替えを判定し、敵・弾・ミサイルを進める。
  3. 描画を 1 回行う。物理ステップ間を補間した姿勢からカメラを決め、すべての物の位置からカメラ位置を引き、惑星の LOD を更新して描き、最後に HUD を 2D キャンバスに描く。

1時間の進め方

物理は固定の刻み、描画は画面の更新に合わせる。

src/core/loop.jssrc/physics/body.js

何が問題か

画面の更新間隔 (60 Hz、144 Hz、処理落ち時はもっと遅い) をそのまま物理の刻み幅にすると、環境によって操縦の効きやばねの跳ね方が変わり、刻みが粗いと着陸装置のばねが発散します。

描画フレームごとに経過時間を「貯金」(acc) に足し、貯金が 1/120 秒以上ある間だけ物理を 1 ステップずつ進めます。残った端数は捨てずに次のフレームへ持ち越します。

const dt = Math.min((now - this.last) / 1000, 0.1); // タブ復帰時などの飛びを抑える
this.acc += dt;
while (this.acc >= this.h) {      // h = 1/120 秒
  this.step(this.h);
  this.acc -= this.h;
}
this.frame(this.acc / this.h, dt); // alpha = 次のステップまでの進み具合 (0..1)

剛体は 1 つ前の位置と向きを覚えていて、描画用の姿勢は位置を線形補間、向きを球面線形補間 (slerp) で求めます。

割り切った点

1 フレームの経過時間は 0.1 秒で頭打ちにしています。長く止まった後は、その分だけゲーム内の時間が遅れます (追いつこうとして物理を何百回も回すより安全です)。

2巨大スケールと精度

このゲームの技術の中心。数値を常に「小さいまま」扱う。

src/game.jssrc/physics/frame.jssrc/camera/cameraRig.jssrc/render/dust.js

何が問題か

浮動小数点数は、値が大きいほど表せる数の間隔が粗くなります。GPU が使う単精度 (float32) は有効数字が約 7 桁しかなく、JavaScript の倍精度 (float64) でも約 16 桁です。恒星を原点にメートルで座標を持つと、遠くでは機体が「がたがた」と飛び飛びに動きます。

解き方: 座標系を入れ子にして、乗り換える

位置を 1 つの座標で持つのをやめ、スケールごとに原点の違う座標系を重ねます。どの段でも、実際に計算する数値は小さく保たれます。

Floating Origin (カメラを原点に置く)

物理の座標はすべて JavaScript の Number、つまり float64 です。float32 になるのは GPU に送る瞬間だけなので、送る前に CPU の倍精度でカメラ位置を引きます。カメラは常に原点にあり、近くの物ほど小さい数値、つまり高い精度で描かれます。遠くの物は粗くなりますが、遠いので画面上では見えません。

同じ考え方を細部でも繰り返しています。

  • 地形チャンク: 頂点はチャンク中心からの相対位置 (float32)、中心だけを float64 で持つ。
  • 宇宙塵: 「カメラ位置 mod 400 m」を CPU の倍精度で計算してシェーダーに渡す。
  • 地面の模様: カメラ位置を 256 m と 8192 m の周期で折り返して渡し、シェーダー内のノイズを惑星に固定する。
  • レイと球の交差: 大きな数どうしの引き算を避けるため、最接近点を経由して解く。
  • 奥行き: 1 m 先の機体と数十万 km 先の惑星が同じ画面に入るので、対数深度バッファを使う。

原点の付け替え

宇宙を飛んでいて機体が世界座標の原点から 10,000 km (RECENTER = 1e7) 離れたら、原点を機体の位置へ移します。機体・弾・敵・爆発の位置から同じ量を引き、天体の世界座標を「星系座標 − 原点」で計算し直します。見た目には何も起きません。

惑星と一緒に回る座標系

惑星は自転しています。慣性系のままだと地表が常に横へ流れていて、「地面に対して止まる」ことが難しくなります。そこで惑星半径の 6 倍より内側に入ったら、機体の状態を惑星ローカル座標に変換します (出るのは 6.6 倍。境目で行ったり来たりしないための幅です)。

\[ \mathbf{x}' = q^{-1}(\mathbf{x} - \mathbf{P}), \qquad \mathbf{v}' = q^{-1}\mathbf{v} - \boldsymbol{\omega}\times\mathbf{x}', \qquad q_{\text{機体}}' = q^{-1}\,q_{\text{機体}} \]

\(q\) は惑星の向き、\(\mathbf{P}\) は惑星の中心、\(\boldsymbol{\omega}\) は自転の角速度です。速度から \(\boldsymbol{\omega}\times\mathbf{x}'\) を引くことで、「地表と一緒に動いている」状態が速度 0 になります。カメラの向きと追従の遅れも同じ回転で変換するので、切り替えの瞬間に画面は飛びません。

星系の乗り換え

恒星から 0.2 光年以上離れると、30 ステップに 1 回、いちばん近い恒星を調べます。別の恒星までの距離が今の恒星までの 0.95 倍より近くなったら、前の星系の惑星を捨て、原点を新しい星系の座標に付け替えます。

割り切った点
  • 惑星ローカル座標の中では、遠心力とコリオリ力を省いています。自転が遅い (出発地の惑星で周期 2 時間) ので影響が小さく、操作が素直になります。
  • 座標系が切り替わるとき、敵と弾はいったん片付けます。切り替わるのは惑星から遠い場所なので、目立ちません。
  • 惑星は公転しません。星系座標での位置は固定です。

6 自由度の剛体と半陰的オイラー法

機体は質量 12 t、主慣性モーメント (対角成分のみ) を持つ剛体です。1 ステップは次の順で進めます。

\[ \mathbf{v} \leftarrow \mathbf{v} + \frac{\mathbf{F}}{m}\,\Delta t, \qquad \mathbf{x} \leftarrow \mathbf{x} + \mathbf{v}\,\Delta t, \qquad \boldsymbol{\omega} \leftarrow \boldsymbol{\omega} + I^{-1}\boldsymbol{\tau}\,\Delta t, \qquad q \leftarrow q \cdot \Delta q(\boldsymbol{\omega}\Delta t) \]

先に速度を更新し、更新後の速度で位置を進めるのが「半陰的」オイラー法です。計算量は普通のオイラー法と同じですが、ばねのような振動する系でエネルギーが増え続けにくく、着陸装置が安定します。角速度は機体座標で持つので、回転のクォータニオンは右から掛けます。

フライトアシスト: 入力は「目標」、推力は制御器が決める

アシスト ON のとき、スティックは力ではなく目標の角速度を指示します。制御器は誤差に比例したトルクを出し、空気が機首を振ろうとするトルクも打ち消します。

\[ \tau = \operatorname{clamp}\!\Big( (\omega_{\text{目標}} - \omega)\,g\,I \;-\; \tau_{\text{空力}},\ \pm\,\alpha_{\max} I \Big), \qquad g = 9\ \text{s}^{-1} \]

スラスターの力に上限 (clamp) があるので、高速では空気の復元力に勝てなくなり、引ける迎角 (つまり G) に自然な上限が生まれます。

並進も同じ形で、場所によって 2 つの操縦方法を混ぜます。

操縦方法スロットルの意味使われる場所
宇宙 / ホバー目標速度。誤差 × 3 s⁻¹ の加速度を出し、重力も打ち消す空気が薄い所、または H
航空機推力そのもの。翼の揚力で飛ぶ空気が濃い所

混ぜる割合は空気密度から決めます。地球の海面の 1%〜8% の密度 (高度およそ 32 km〜18 km) にかけて smoothstep で 0 から 1 へ変わるので、大気圏に入ると操縦の感覚が切り替わりではなく徐々に移ります。

空気力

機体座標での対気速度から迎角 \(\alpha\) を求め、動圧 \(q=\tfrac12\rho V^2\) と翼面積 \(S\) から揚力と抗力を計算します。

\[ L = q\,S\,C_L(\alpha), \qquad D = q\,S\,C_D(\alpha, M) \]
  • 抗力: 最小抗力 + 誘導抗力 (\(k\,C_L^2\)) + 着陸装置 + 造波抵抗。造波抵抗はマッハ 0.85 から立ち上がり 1.15 で最大、それ以上は \(1/\sqrt{M}\) で減ります。海面での最高速度が約 400 m/s に落ち着くのはこの「音の壁」のためです。
  • 風見安定: 機首を進行方向へ戻すトルクと、回転を弱める減衰。
  • 空力加熱: 目標値を \(\sqrt{\rho/\rho_0}\,V^3\) に比例させ、一次遅れで追わせる。100% を超えた分が損傷になります。

接地: ばね・ダンパー・摩擦

脚 3 本と機体の数点 (腹・翼端・機首・背中) を接地点とし、地面にめり込んだ深さに比例する反力と、めり込む速さに比例する減衰をかけます。地面は、機体の真下と 2 m 離れた 2 点の標高から求めた平面で近似します。摩擦は「速度に比例、ただし \(\mu N\) で頭打ち」という形にして、止まる直前に力の向きが振動するのを防いでいます。高速で突っ込んだときのすり抜け防止として、機体の中心が地面に近づきすぎたら強制的に押し戻します。

巡航の速度則

巡航中の最高速は、いちばん近い天体 (惑星の地表または恒星の表面) までの距離 \(d\) だけで決まります。

\[ v_{\max} = 400\ \text{m/s} \times \max\!\Big(5,\ \frac{\min(d,\,10^6)}{3000} + \frac{\max(0,\ d-10^6)}{1200}\Big) \]

天体に向かって全開で飛ぶと \(\dot d = -d/7.5\) となり、距離は 7.5 秒ごとに \(1/e\) になります。どれだけ遠くから来ても、近づくにつれて同じ調子で減速し、地表の手前で通常の速度に戻ります。上限はないので、惑星間は約 2 分、5 光年先の恒星まで約 3.5 分です。

巡航を切ったときは、速さを \(v(t)=v_0\,(v_{\text{終}}/v_0)^{t/T}\) (\(T=2.5\) 秒) に沿って落とします。毎秒同じ比率で減るので、光速の何倍からでも同じ 2.5 秒で 400 m/s になります。

割り切った点
  • ジャイロ項 (\(\boldsymbol{\omega}\times I\boldsymbol{\omega}\)) を省略。操縦系が常に角速度を制御しているので、効果が見えません。
  • 重力は「いま座標系に入っている惑星」の分だけ。宇宙空間では無重力で、軌道運動はありません。
  • 巡航中は重力も空気も無視します。物理的な加速ではなく「ドライブ」という設定です。

4無限の宇宙の自動生成

何も保存しない。場所から毎回同じものを計算する。

universe/galaxy.jsuniverse/system.jsmath/random.js

何が問題か

どこまで飛んでも星があり、戻ってきたら同じ星がある宇宙にしたい。しかし無限の宇宙をデータとして持つことはできません。

空間を一辺 10 光年の区画に分け、区画の番号 (整数 3 つ) をハッシュして乱数の種にします。種が同じなら乱数列は必ず同じなので、その区画の恒星は何度作っても同じになります。

export function sectorSeed(ix, iy, iz, salt = 0) {
  let h = Math.imul(salt + 1, 0x9e3779b1);
  h = mixIn(h, ix);   // 軸ごとに順番に混ぜ込む (MurmurHash3 の 1 ブロック分)
  h = mixIn(h, iy);
  h = mixIn(h, iz);
  h ^= 12;
  h = Math.imul(h ^ (h >>> 16), 0x85ebca6b);   // ビットをよくかき混ぜる
  h = Math.imul(h ^ (h >>> 13), 0xc2b2ae35);
  return (h ^ (h >>> 16)) >>> 0;
}

区画の中身の決め方

  • 乱数生成器は mulberry32。32 ビットの状態 1 つだけの小さな生成器で、速く、種から完全に再現できます。
  • 恒星の数は 0 個 25%、1 個 40%、2 個 25%、3 個 10%。
  • 位置は、他の恒星から 1.5 光年以上離れた場所が見つかるまで最大 8 回引き直します。区画の端 0.75 光年には置かないので、隣の区画の恒星とも近づきすぎません。
  • 種類は重み付きの抽選 (赤色矮星 42% 〜 青白色巨星 2%)。名前は音節の表から 2〜3 個つなげて作ります。
  • 計算済みの区画は 4,000 個までキャッシュします。

星系

恒星ごとに決まる種から、惑星の数・種類 (海洋・砂漠・氷・溶岩・岩石・ガス巨星)・半径・自転周期・大気の色、衛星、小惑星帯、敵の哨戒隊を決めます。惑星は地形の種を持つだけで、地形そのものは近づいたときに初めて計算されます (次章)。出発地の SOL 星系だけは太陽系に似せて手で配置してあります。

割り切った点

恒星の密度は銀河のどこでも同じで、渦巻きの腕や中心といった大きな構造はありません。背景の天の川は見た目だけの別の星空です。

5地形生成

惑星の地形は「方向を入れると標高が返る関数」ひとつ。

terrain/noise.jsterrain/terrainFn.js

地形のデータは持ちません。height(x, y, z, minWL) は、惑星中心から見た方向 (単位ベクトル) を受け取り、その方向の標高 (m) を返します。メッシュを作る Worker も、接地判定をするメインスレッドも、同じ定義から作った同じ関数を呼ぶので、見えている地面と当たる地面が必ず一致します。

材料: パーリンノイズと fBm

土台は 3 次元のパーリンノイズです。格子点ごとに決まった勾配ベクトルを置き、5 次の補間 \(6t^5-15t^4+10t^3\) でなめらかにつなぎます。格子点の割り当て表は惑星の種でシャッフルするので、惑星ごとに違う地形になります。球面の方向ベクトルをそのまま 3 次元の入力にするので、球のどこにも継ぎ目や極のゆがみができません。

これを周波数を約 2 倍、振幅を半分にしながら重ねたものが fBm (非整数ブラウン運動) です。

\[ \operatorname{fbm}(\mathbf{p}) = \sum_{i=0}^{n-1} \frac{1}{2^{i}}\ \operatorname{noise}(2.03^{\,i}\,\mathbf{p}) \]

重ねる回数 \(n\) は、波長が minWL より短くなる手前で打ち切ります: \(n = \lfloor\log_2(R/(f_0\cdot\text{minWL}))\rfloor + 1\)。

標高の組み立て

層技法ねらい
ドメインワープノイズを引く位置を、別のノイズで 0.2 だけずらす海岸線や山脈が丸い塊ではなく、うねった形になる
大陸低周波の fBm + 陸の多さ (land)標高 0 を境に海と陸が分かれる
山脈尾根ノイズ \((1-|n|)^2\) を、陸の内側と低周波のマスクの中だけに立てる鋭い稜線が、帯状に連なる
丘陵侵食風の fBm (下記)水に削られたような斜面
クレーター格子配置 (下記)。大気や水のある天体では浅くする岩石天体らしい表面

侵食風のノイズ

本物の侵食シミュレーションは、周囲の広い範囲を何度も計算する必要があり、「1 点だけ評価する関数」にはできません。代わりに、ノイズの解析的な勾配 (noiseD が値と一緒に返す) を使います。オクターブを重ねるとき、それまでに積もった斜面の急さ \(\mathbf{s}\) に応じて細部を弱めます。

\[ h \mathrel{+}= \frac{a_i\, n_i}{1 + 0.7\,|\mathbf{s}|^2}, \qquad \mathbf{s} \mathrel{+}= 0.75^{\,i}\ \nabla_{\!\text{水平}}\, n_i \]

急な斜面はなめらかに、尾根の上と谷底 (勾配が 0 に近い所) には細部が残ります。各オクターブの弱め方はそれより粗いオクターブだけで決まるので、細部を省いた粗いメッシュでも大きな形は変わりません。

クレーター

空間を立方体の格子に区切り、区画番号のハッシュで「クレーターがあるか・中心・半径・古さ」を決めます (銀河の恒星と同じ考え方)。評価する点のまわり 3×3×3 区画だけを調べれば、その点に届くクレーターがすべて見つかります。格子の細かさを 2.6 倍ずつ変えて 8 層重ねることで、大小さまざまなクレーターになります。小さいものはお椀形、大きいものは底が平らで壁が急になり、半径 8 km を超えると中央丘ができます。

割り切った点
  • 川や谷のような、水の流れがつながった地形は作れません (1 点評価の関数の限界)。
  • 海面より下はメッシュでは平らな水面にします。海底の形は色 (浅瀬の明るさ) にだけ使います。

6惑星の LOD

宇宙からは粗く、地表では頂点間隔 1.2 m まで細かく。

planet/planetLod.jsterrain/chunkBuilder.jsterrain/terrainWorker.js

何が問題か

半径 400 km の惑星を頂点間隔 1.2 m で全部メッシュにすると、頂点は約 1 兆個必要です。カメラの近くだけを細かくする仕組み (LOD: Level of Detail) が要ります。

キューブ球と四分木

立方体の 6 面をそれぞれ格子に切り、各点を中心からの距離が 1 になるよう正規化して球面に押し出します (キューブ球)。緯度経度の格子と違って極に点が集まらず、各面が正方形なので四分木にそのまま載ります。

各面は 1 枚のチャンク (32×32 マス) から始まり、カメラが近づくと 4 枚の子に分かれます。どの深さのチャンクも頂点数は同じで、覆う範囲が半分ずつになります。半径 400 km の惑星では 14 段で頂点間隔が約 1.2 m に達します。

const k = SPLIT_K * (node.children ? MERGE_HYSTERESIS : 1);  // 1.3、分割済みなら × 1.15
const wantSplit = node.level < this.maxLevel && d < node.size * k;

分割済みのノードには 1.15 倍の余裕を持たせます。境目のすぐそばを飛んでも、分割と統合が毎フレーム入れ替わることがありません。

穴と隙間を出さない工夫

  • 子が 4 枚そろってから切り替える: 子のメッシュは Worker で作るので、できあがるまで時間がかかります。そろうまでは親を表示し続けます。
  • スカート: 隣り合うチャンクの細かさが違うと、境目の頂点が合わずに隙間が見えます。各チャンクの縁から、惑星の中心方向へ帯 (チャンクの大きさの 5%、最低 2 m) を垂らして隙間をふさぎます。隣の細かさを調べて縁を縫い合わせる方法より、はるかに単純です。
  • 法線の継ぎ目: 法線は隣の頂点との差から求めます。チャンクの外側 1 周ぶんも標高を計算しておくので、縁の法線が隣のチャンクと一致し、明るさの段差が出ません。

Web Worker で裏で作る

チャンク 1 枚の生成は、標高関数を 35×35 回呼ぶ重い計算です。メインスレッドで行うと画面が止まるので、Worker (別スレッド) に任せます。

  • Worker の数は CPU のコア数 − 2 (2〜6 個)。全惑星で 1 組を共有します。
  • 待ち行列からは 「距離 ÷ 大きさ」が最も小さいチャンク、つまり画面で最も大きく見えるものを先に取り出します。
  • カメラが通り過ぎて不要になったチャンクの仕事は、順番が来た時点で捨てます。
  • できあがった頂点配列は Transferable として渡すので、スレッド間でコピーが起きません。
  • 三角形のつなぎ方 (インデックス配列) は全チャンク共通で、1 つだけ作って使い回します。
割り切った点

LOD が切り替わるとき、形がわずかに「ぱっ」と変わります (ジオモーフィングなし)。チャンクが十分に小さく見える距離で切り替わるので、実際にはほとんど気になりません。

大気散乱

何が問題か

宇宙から見た青い縁、昼の青空、夕焼け、遠くの山のかすみ。これらを別々の演出として作ると、高度を変えたときにつながりません。

これらはすべて、太陽光が空気の分子 (レイリー散乱) と微粒子 (ミー散乱) に当たって向きを変える、同じ現象です。視線に沿って大気の中を少しずつ進み、各点で「太陽からその点まで届いた光」が「カメラの方へ散乱される量」を足し合わせます。

\[ L(\text{視線}) = I_{\text{太陽}} \sum_{i} \Big[ \beta_R\,P_R(\mu)\,\rho_R(h_i) + \beta_M\,P_M(\mu)\,\rho_M(h_i) \Big]\ e^{-\tau(\text{カメラ}\to i)\,-\,\tau(i\to\text{太陽})}\ \Delta s \]
  • \(\rho(h)=e^{-h/H}\): 高度とともに薄くなる空気。スケールハイト \(H\) はレイリーが 7 km、ミーが 1.4 km。
  • \(\beta_R\): レイリー散乱係数。赤 5.2、緑 12.1、青 29.6 (×10⁻⁶ /m)。青が赤の約 6 倍散乱されることが、空が青い理由です。
  • \(P_R(\mu)=\tfrac{3}{16\pi}(1+\mu^2)\): 散乱の向きの偏り。\(\mu\) は視線と太陽方向のなす角の余弦。
  • \(P_M\): ミー散乱は前方に強く偏ります (\(g=0.76\))。太陽のまわりの白いにじみになります。

この scatter() という 1 つの GLSL 関数を、空 (大気の殻) のシェーダーと地表のシェーダーの両方が使います。空では視線が大気を抜けるまで、地表ではカメラから地面までを積分し、地面の色に透過率を掛けて散乱光を足します。惑星ごとの違い (砂漠の黄土色の空、溶岩惑星の赤茶色の空) は、係数を変えるだけです。大気のない天体は係数 0 の大気として扱い、同じシェーダーを通します。

地面の細部

頂点間隔 1.2 m のメッシュと頂点色だけでは、近くで見るとのっぺりします。シェーダーの中でノイズを計算して、模様と凹凸を足しています。凹凸は、画面上の隣のピクセルとの差 (dFdx, dFdy) から高さの傾きを求めて法線を傾ける方法で、テクスチャも UV 座標も要りません。細かい模様ほど近くでだけ見せ、遠くではちらつくので消します。水面は、向きの違う 2 枚のノイズを流して波にし、太陽の反射・空の映り込み・波打ち際の白波を加えています。

岩と木

  • 地表をキューブ球の格子で区切り、区画番号のハッシュから置き場所を決めます (銀河・クレーターと同じ考え方)。離れて戻っても同じ木が同じ場所にあります。
  • 同じ形を大量に描くので InstancedMesh を使い、形状 1 つと個体ごとの行列だけを GPU に渡します。
  • 木は 350 m より遠くをビルボード (絵を貼った板) に切り替え、3 km 先まで描きます。1 本につき、幹を軸にカメラへ回る縦の板と、真上から見た絵の水平な板の 2 枚を使うので、上空から見下ろしても木が線になりません。絵はメッシュの木と同じ形を canvas に描いて作ります。

宇宙の背景

  • 背景の星空: カメラと一緒に動く点の集まり。無限遠にあるように見えます。
  • 近くの恒星: 銀河の生成結果から、実在する恒星を本当の方向に描きます。飛ぶと位置がずれて見え、近づいた恒星はそのまま太陽になります。
  • 宇宙塵: 何もない空間で速度感を出すための粒。400 m の立方体にばらまいた 1,400 個を、シェーダーの mod でカメラのまわりに無限に繰り返します。
割り切った点
  • 散乱は 1 回だけ考えます (多重散乱なし)。積分は毎ピクセル数十回の計算で、事前計算の表は使っていません。
  • 影は、惑星の影に入ったかどうかだけ。地形や機体が落とす影はありません。
  • 岩と木に当たり判定はありません。

見越し点

弾は実体として飛ぶので、動く的には「今いる場所」ではなく「弾が届く頃にいる場所」を狙う必要があります。弾は射手の速度に弾速 \(s\) を上乗せして飛ぶので、射手から見た相対位置 \(\mathbf{r}\)・相対速度 \(\mathbf{v}\) で考えると、命中の条件は次の式になります。

\[ |\mathbf{r} + \mathbf{v}\,t| = s\,t \quad\Longrightarrow\quad (\mathbf{v}\!\cdot\!\mathbf{v} - s^2)\,t^2 + 2(\mathbf{r}\!\cdot\!\mathbf{v})\,t + \mathbf{r}\!\cdot\!\mathbf{r} = 0 \]

この 2 次方程式の最小の正の解 \(t\) が命中までの時間で、見越し点は「的の位置 + 的の速度 × \(t\)」です。解がなければ、弾が的に追いつけません。

HUD に出る緑の丸がこの点です。見越し点が機首から 2° 以内にあるとき、砲はそちらへ自動で向きます。

弾: 配列にまとめ、線分で当たりを調べる

  • 弾は数が多いので、1 発ずつオブジェクトにせず、位置・寿命・威力をそれぞれ 1 本の数値配列にまとめて持ちます。メモリの確保と解放が起きず、処理も速くなります。
  • 弾は 1 ステップで数 m 進むので、「今の位置が的の中か」だけを調べると飛び越えてしまいます。1 ステップで動いた線分と、的を包む球との交差を調べます。
  • 地形や小惑星との判定は重いので、6 ステップに 1 回、その間に動いた線分でまとめて調べます。

ミサイルの誘導

ミサイルは的までの距離と接近する速さから残り時間 \(t_{go}\) を見積もり、「その時間で的に届く速度の向き」を求めます。

\[ t_{go} = \frac{|\mathbf{r}|}{v_{\text{接近}}}, \qquad \hat{\mathbf{d}}_{\text{目標}} = \operatorname{normalize}\!\Big(\frac{\mathbf{r}}{t_{go}} + \mathbf{v}_{\text{的}}\Big) \]

進行方向をこの向きへ回しますが、1 ステップに回せる角度は「横加速度 200 m/s² (約 20 G) ÷ 速さ」までです。速いほど曲がれないので、的が鋭く旋回すると振り切れます。的が進行方向から 60° 以上外れると見失い、そのまま直進します。

敵 AI

敵機は自機と同じ Ship クラスで、同じ空気力・同じ推力の上限で飛びます。AI は毎秒 20 回ほど判断して操縦入力を書き換えるだけです。物理を無視した動きができないので、人間が見て納得できる飛び方になり、機体の調整値を変えれば敵の飛び方も一緒に変わります。

  • 行き先 → 操縦入力: 行き先の方向を機体座標に直し、上下・左右のずれに比例してピッチとヨーを出します。大きく向きを変えるときは、人間と同じように「行き先が真上に来るまでロールしてから引く」動きをします。
  • 狙いの積分項: 動く的を比例制御だけで追うと、いつも少し遅れます。照準中 (ずれが 0.3 rad 以内) だけ誤差の積分を足して、遅れを消します (PI 制御)。
  • 腕前: 0〜1 の値で、狙いのぶれと撃ち始める角度が変わります。
  • ぶつからない: 速さと降下角から、引き起こしに必要な高さ (約 6 G で回る円弧の落差) を計算し、足りなければ上昇を最優先にします。進む先の地面の高さと、近くの小惑星も調べます。
割り切った点
  • 敵どうしの連携 (挟み撃ちなど) はありません。1 機ずつ独立に判断します。
  • 敵は巡航を使わず、60 km 離れると引っ込みます。座標系をまたぐ追跡はしません。

全体を通して繰り返し出てくる考え方

  • 場所から決める: 恒星・クレーター・岩・木は、どれも「区画番号 → ハッシュ → 乱数の種」で決まります。保存も通信も要らず、どこまでも続きます。
  • 数値を小さく保つ: 基準点を近くに置き、差だけを単精度で扱います。座標系の階層、チャンクの中心、塵の位相、シェーダーの模様がすべてこの形です。
  • 1 つの定義を共有する: 標高関数は描画と当たり判定で、散乱の式は空と地表で、飛行モデルは自機と敵機で共有します。食い違いが原理的に起きません。
  • 境目に幅を持たせる: LOD の分割と統合、座標系の出入り、操縦方法の切り替えは、どれも境目に余裕やなめらかな移り変わりを入れて、ちらつきを防いでいます。
